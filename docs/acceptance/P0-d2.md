## 4. 真实性依据（为什么不是“绿了就算”）

1. **真实 QEMU，不是 canned 日志。** CI 的 boot step 是 `bash tools/boot-check.sh --artifact out/artifact.json --timeout 600 --json`，**没有** `--log-from`。job log 明确打印 `launching qemu-system-x86_64 (iso/OVMF, -cdrom, timeout 600s)`，boot.log 含 OVMF `BdsDxe`、`QEMU DVD-ROM`、动态内核时间戳与 15.156s 启动统计，不是静态 fixture。
2. **ISO 模式确实用 `-cdrom` 且不挂磁盘。** `tools/boot-check.sh:1548-1550` 在 `boot.mode=iso` 分支只追加 `-cdrom "$ISO_ABS"`；UEFI 分支的磁盘 `-drive file=…,if=virtio` 不执行。`boot-check-test` 的 ISO argv 测试对完整 argv 做逐项断言，并额外断言 `only the two pflash drives=2`、`no virtio disk drive=0`、`no raw disk path=0`、无 `-kernel`/`-initrd`/`-append`。boot.log 中 `vda`/`virtio_blk` 均为 0，只有 `QEMU DVD-ROM`/`CD-ROM`。
3. **断言谓词与 evidence 写入使用同一套实现。** `all_assertions_pass`（QEMU 早停监控）和 `evaluate_assertions`（evidence 写入）都调用 `log_has`/`log_has_ci`，6 条断言在两边一致；不存在“监控用一套、报告用另一套”的假通过路径。`determine_result` 对 ISO 额外要求 `boot.live=pass`，否则 `result=fail`。
4. **真实 boot.live 证据链。** boot.log 有 live-boot 的挂载行 `Begin: Mounting "/run/live/medium//live/filesystem.squashfs" … via "/dev/loop0" … done.`，同时有 `boot=live live-media-path=/live`、`squashfs: version 4.0`；随后 systemd 从该 rootfs 启动并到达 login。即使 `overlay` 的命中是负向 EVM 行，`boot.live` 仍由挂载行 + squashfs + live-media 共同成立。
5. **负例确实会 fail。** 本地 boot-check 测试包含 `ISO log without live marker -> boot.live fail, exit 1`；我用真实 CI boot.log 删除所有 `squashfs`/`live-media`/`overlay` 行后重放，得到 `boot.live=fail`、`result=fail`、exit 1，其余 5 条仍 pass——说明 `boot.live` 不是恒真。
6. **证据完整性。** zip sha256 与 GitHub digest、job log 上传摘要三方一致；zip 内 5 个文件与 `gh run download` 解包文件逐字一致；job log 打印的 evidence JSON 与下载文件值一致；`log_sha256` 与 `boot.log` 实测一致。任何单点篡改都会破坏其中至少一处。
7. **构建命令真实。** build.log 记录了 `mmdebstrap`、`mksquashfs`、`grub-mkstandalone`、`mkfs.vfat`、`mcopy`、`xorriso` 的实际 argv 与工具输出；boot.log 的 kernel 版本、GRUB 版本、OVMF 版本与这些步骤一致。
8. **CI 没有掩盖失败。** `.github/workflows/ci.yml` 中无 `continue-on-error`；boot step 没有 `|| true`；上传步骤虽为 `if: always()`，但 job 的最终状态由 boot-check 的退出码决定，不会把失败“洗绿”。
