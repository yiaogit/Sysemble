### 3.8 失败路径（V8 的独立补测）

## 7. 风险与限制

1. **arm64-only，不是 x86_64 目标**。E3a 镜像是 arm64 Debian rootfs，helper 没有 UEFI/GRUB 路径；x86_64 仍由 P1-e2 容器后端承担。不能把本原型宣传成“macOS 上产出可启动 x86_64 镜像”。
2. **CI 不能启 VZ**。GitHub macOS runner 自身是 VZ guest，`probe` 明确 `supported=false`（`Virtualization is not available on this hardware`）；CI 只证明编译/签名/probe，真实启动只在本机与用户设备。README/workplan 已如实区分，CI 日志没有“已启动”的表述。
3. **ad-hoc entitlement 的限制**。二进制只做 ad-hoc 签名，无 Developer ID/notarization；macOS **13/14 未实测**（本机 26.6.2，CI 15.8.2 且不能启 VM）；受管 Mac 可能在 `VZVirtualMachine` start 时拒绝，尽管 `validate()` 通过。`probe` 只能证明 `validate()` 接受签名。
4. **非位级可复现**。同一 kernel（`d6d5…`）在三次构建中一致，但 initrd/disk 每次不同（CI `c970…`/`b246…`、本机旧镜像 `0bdd…`/`bbde…`、本机新构建 `a7d2…`/`4c37…`）；rootfs tar 也因 mmdebstrap 时间戳而不同（本机本次 `fd8e…`，README 记录的开发机旧 run 为 `1ee9…`，但条目数同为 19,301）。`disk.img` 的 sha256 只在单次构建内可核对，跨构建不可比。
5. **V10 用户设备半边未发生**。需要用户在另一台 Apple Silicon Mac（macOS 13+）上执行 §7.1 的命令；本会话无法代替。该半边保持 **BLOCKED**，不写成 PASS/FAIL。
6. **serial 缺少最早的内核横幅**。本次 `vm-serial.log` 从 0.131s 开始，未见 `Linux version` 首行；内核启动行、virtio 设备、systemd、`hvc0` 均完整，V4 判定不受影响，但排障时要知道日志不保证包含最早几行。
7. **artifact 不含 6 GiB `disk.img`**。CI 的 disk sha256 只能通过 CI 自身的 `image_test` 和 build log 交叉，不能在本机对 CI 盘独立复算；本机 `--verify` 才是完整三方校验。
8. **共享盘语义与容量**。virtiofs 落在 APFS（默认大小写不敏感）；协议只用 ASCII 文件名，guest 在 `/out` 构建，但这仍是约束。6 GiB 稀疏盘、`--no-clone` 会写原盘、日志不设上限；这些都在 README 的 Known limits 里。
9. **`probe` 的 CI 语义**。CI 上 `entitled=false` 是“签名/硬件不可用”的探测结果，不是构建失败；本次 CI 的 `probe` 仍 exit 0，测试以 SKIP 处理，符合契约。
