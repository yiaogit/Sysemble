## 6. 契约偏差与风险（不判失败，但需记录）

### R1 — B7：fixture 与真实 plan 显著不同，易误导使用者（高）

`builders/debian/testdata/plan.example.json` 是手写 fixture，不是 `debian-kde-dev.yaml` 的真实 resolver 输出；但 `builders/debian/README.md` 的 dry-run 示例直接展示 "57 packages / 4300 MB"，读者很容易把它当作真实 plan。实际：

| 指标 | fixture | 真实 plan |
|---|---|---|
| packages | 57 | 34 |
| image_mb | 4300 | 5220 |
| build_minutes | 38 | 49 |
| disk_mb | 12000 | 11464 |
| modules | 7 | 9 |
| warnings | 1 | 0 |

额外差异：

- fixture 有 35 个真实 plan 没有的包，真实 plan 有 12 个 fixture 没有的包；
- fixture 的 module 列表（`desktop-apps`、`security-hardening` 等）与真实 plan（`base-debian`、`containers`、`installer`、`security` 等）结构不同；
- fixture 的唯一 warning 是 `windows.remoteapp.untested`，该 code **不在 core 的稳定 code 表**中，真实 plan 对该示例是 **0 warnings**。

建议：把 fixture 明确标注为“合成契约样例，不代表任何示例的 resolver 输出”；或在合并前用真实 `plan` 输出重新生成 fixture，并更新 builder README 的 57/4300 文案。**不影响 B1**（B1 用真实 plan 验证了 34 包一致），但会影响文档可信度与后续回归的直觉。

### R2 — 真实 plan 不含内核/initramfs，P0-b 真实构建可能不可启动（高）

真实 `debian-kde-dev` plan 只有 34 个包，其中**没有 `linux-image-*`、没有 `initramfs-tools`、没有 `systemd-sysv`/`udev`**；而 fixture 恰好包含这些。`crates/sysemble-core/src/packages.rs` 的注释明确说明 P0 不把 `system.kernel` 映射为包，builder README 也说明“plan 的 packages 应已包含 base/desktop/dev 包”。`mmdebstrap --variant=minbase` 默认不安装内核。

P0-a 只做 dry-run，所以不构成本轮失败；但进入 P0-b 实际构建/启动时，必须先决定内核与 initramfs 由 resolver（推荐）还是 builder 负责，否则 rootfs 不可引导。fixture 中的 `linux-image-amd64` 会掩盖这个缺口。

### R3 — builder 不应用 `base.pin` / `target.arch`；docker 用移动 tag（中）

- `--dry-run` 显示 `pin`，但真实命令未传给 mmdebstrap，快照钉版未生效；
- `target.arch` 只校验、不传给 mmdebstrap；在 arm64 宿主机上计划 x86_64 时，真实构建会构建宿主架构；
- docker 模式使用 `debian:trixie` 移动 tag。

这些都在 `builders/debian/README.md` 中声明为 P0-a 限制，但对“可复现”与跨架构是实质风险，P0-b 需处理（或明确把 x86_64 构建限制在 x86_64 引擎上）。

### R4 — 文档与真实输出不同步（中）

- `docs/plan/P0-workplan.md` A6 写 `firefox`，实际 Debian 映射为 `firefox-esr`（任务书 A6 已改为 `firefox-esr`，说明工作单文字滞后）；
- 同一文件 §2.1 的示例 plan 写 `image_mb: 4300`、`build_minutes: 38`、`disk_mb: 12000`、只有 `desktop-plasma` 一个模块、带 `windows.remoteapp.untested` warning；真实输出是 `5220/49/11464`、9 个模块、0 warnings；
- 根 `README.md` 仍写 "design phase ... build engine is not implemented"，与 P0-a 已交付 CLI/plan/builder 不符。

建议在合并前统一更新；契约的**结构**（字段名/类型）与实现一致，问题在示例值和状态文案。

### R5 — 工作单 A10（CI）未验证（中）

`docs/plan/P0-workplan.md` 的 A10 是“推送后 GitHub Actions 两个 job 绿”。本任务把 A10 重新定义为工作区检查，已 PASS；但 `.github/workflows/ci.yml` 的两个 job（schema + rust）**没有在本轮运行**（无 push、无网络）。CI 是 A7 的兜底，必须在主线程推送后确认。

### R6 — `plan` 对“合法但不支持”的 base 返回 1，契约措辞是“spec 无效”（低）

`examples/minimal-alpine.yaml`：`validate` exit 0（语义合法），`plan` exit 1：

```text
error: base `alpine` is not supported by the P0 planner (supported: debian, ubuntu)
```

CLI 契约表把 `plan` 的 exit 1 描述为“spec 无效”，但这里 spec 是有效的，只是 P0 planner 不支持。建议文档区分“invalid”与“unsupported”，或未来用独立退出码；当前行为本身合理，不判失败。

### R7 — 人类可读的 parse-error 诊断格式与语义诊断不一致（低）

语义错误：`error[spec.api_version.unsupported] /apiVersion: ...`；
YAML/未知字段 parse 错误：`error: cannot parse spec ...`（无 `error[code] /path`）。
`--json` 会把 parse 错误包装成 `spec.parse`（path `/`），机器消费一致；但 `validate --help` 声称诊断格式为 `error[code] /path: message`。A4 只要求 stderr 含 `bogus`，已 PASS；此不一致属于消费方体验风险。

### R8 — Docker 构建路径未验证（中）

macOS 上 `docker info` exit 1，daemon 未运行。本轮按任务要求没有启动 daemon，也没有执行 `--engine docker`；builder README 自述 docker 路径仅用 stub 验证过。P0-b 前需要在有 daemon 的 Linux/macOS 上做一次真实 dry-run + 最小构建验证（并注意 `--privileged` 的风险边界）。

### R9 — 工作区交付尚未提交，`Cargo.lock` 未跟踪（流程）

A10 确认当前 25 条变更都在预期目录，但它们是**未提交交付**：4 个已跟踪文件修改 + 21 个未跟踪文件（含 `Cargo.lock` 与本报告）。主线程在合并前应 review 全部路径、提交 `Cargo.lock`（保证依赖可复现），再推送跑 CI。
