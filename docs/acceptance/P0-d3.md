## 5. 真实性依据（为什么不是“绿了就算”）

### 5.1 真磁盘、真 QEMU、两阶段，不是桩

| 判据 | 证据 |
|---|---|
| 真建 6 GiB 磁盘 | `tools/install-check.sh:961-971` `create_disk()` 用 `truncate -s 6G`；CI 打印 `disk: …/disk.img (6 GiB sparse raw)`；guest 端 `mkfs.ext4` 看到 `1441531 4k blocks`（≈5.5 GiB 根分区） |
| QEMU phase 1 参数 | `install-check.sh:1019-1031`：`-machine q35 -m 1024 -smp 2 -nographic -no-reboot` + OVMF pflash ×2 + `-cdrom <iso>` + `-drive file=disk.img,format=raw,if=virtio`；`disk.img` 与 guest 的 `/dev/vda` 对应 |
| 真 QEMU 进程 | `install.log` 末尾 `qemu-system-x86_64: terminating on signal 15 from pid 20997 (bash)`——这是 install-check 的 `stop_qemu` 真实发信号；`install-boot.log` 末尾同理由 pid 21244 发出 |
| QEMU phase 2 是**另一个**进程/另一次启动 | 两份日志的固件启动目标不同（`UEFI QEMU DVD-ROM` vs `UEFI Misc Device`）、GRUB 版本不同（2.14 vs 2.12）、cmdline 不同（`boot=live` vs `root=UUID`），且 phase 2 由 `boot-check.sh` 驱动 |
| phase 2 用**同一块**盘 | `run_boot_phase()` 写 `boot-artifact.json` 指向 `disk.img` 并调用 `boot-check.sh`；`boot-check` uefi 分支 `-drive file=…disk.img,format=raw,if=virtio`（`tools/boot-check.sh:1554`）；UUID 与 phase 1 一致 |
| 不是 `--dry-run`/假工具链 | CI 用真 `sgdisk/mkfs/rsync/grub-install`（日志有版本与设备级输出）；`--dry-run` 仅在离线 `installer_test.sh` 中出现 |

### 5.2 marker 的归属：安装器脚本，不是 boot-check

- `builders/debian/installer/sysemble-install.sh:417`：`printf 'SYMBLE: install complete\n' | tee "$CONSOLE"`——marker 是安装器成功路径的**最后一步**，之后才 `systemctl poweroff -f`（`:418`）。
- `install.log:849` 的 journal 行把该消息归属到 `sysemble-install[794]`；`:848` 的裸行来自 `tee /dev/ttyS0` 的 console 输出；脚本顺序上两者都在 `cleanup_mounts`（step 7/7）**之后**、`poweroff` **之前**（`EXT4-fs … unmounting` 的 printk 与 marker 行在串口输出里交错一行，时间戳仍早于 poweroff）。
- `tools/install-check.sh` 全文只有 `grep -Fq "$INSTALL_MARKER"`（`:977-982`、`:1046-1104`）与把 marker 写入 **evidence**（`:1081`、`:1249`）；它**从不写 `install.log`**——该文件只由 `: >"$INSTALL_LOG"`（`:897`）创建、随后由 QEMU 重定向（`:1043`）。
- `tools/boot-check.sh` 全文 **0** 处 `SYMBLE`：boot 阶段根本不知道安装 marker 的存在，不可能伪造。
- 反向证据：安装后的系统里 `install-boot.log` 中 `SYMBLE`/`sysemble-install` 出现 **0** 次——`ConditionKernelCommandLine=sysemble.install` 生效，安装器没有在首次启动时二次运行（否则会再次 `sgdisk -Z` 抹盘）。

### 5.3 安装是真的写进了盘：从“新 UUID”闭环

1. phase 1：`mkfs.ext4` 生成 `Filesystem UUID: 994891cb-c054-4536-83a9-e9d76c9bc43f`（`install.log:803`），安装器随后读回同一 UUID（`:810`）。
2. phase 1：`grub-install` 报告 `Installing for x86_64-efi platform.` + `Installation finished. No error reported.`（`:830`、`:834`）。
3. phase 2：固件从 **virtio 磁盘**（`UEFI Misc Device`）启动，GRUB 读出 **安装盘内的** `grub.cfg`（菜单项 `Sysemble`，非 ISO 的 `Sysemble Live`），cmdline `root=UUID=994891cb-…`，内核把 `vda2` 挂成根。
4. phase 2：systemd 依据安装器写的 `/etc/fstab` 成功挂载 `boot-efi.mount - /boot/efi`（`install-boot.log:664-665`）——**fstab 的 ESP UUID 在真实系统上被验证有效**。
5. 全盘闭环：若安装器没真正分区/格式化/写盘，phase 2 不可能出现新 UUID 的 ext4 根、安装盘自带的 GRUB 配置和可用的 fstab。

### 5.4 phase 2 启动的是磁盘，不是又启动了 ISO

| 判据 | `install.log`（live ISO） | `install-boot.log`（磁盘） |
|---|---|---|
| 固件启动目标 | `UEFI QEMU DVD-ROM QM00005`，`Sata(0x2)` | `UEFI Misc Device`，`Pci(0x3,0x0)`（virtio 盘） |
| GRUB | **2.14**（host `grub-mkstandalone`） | **2.12-9+deb13u4**（chroot 里的 trixie `grub-efi-amd64`） |
| 菜单项 | `Sysemble Live` | `Sysemble`（安装器生成的 `grub.cfg`） |
| cmdline | `boot=live live-media-path=/live …` | `root=UUID=994891cb-… rw console=ttyS0 …`（**无** `boot=live`） |
| live 标记 | `live-boot`/`live-media`/`squashfs` 命中 **5** 行 | 三者均 **0** 行 |
| 根文件系统 | live-boot 把 `/run/live/medium//live/filesystem.squashfs` 挂到 `/run/live/rootfs/…`（`/dev/loop0`，`install.log:493`） | `EXT4-fs (vda2)`，块设备名 `vda` 出现 4 次 |

> 观察（已排除误报）：`install-boot.log` 里确实出现 `ata3.00: ATAPI: QEMU DVD-ROM`。这**不是** ISO 被再次挂载：同 run 的 `boot-smoke`（P0-c 纯磁盘 UEFI 启动，`boot.mode=uefi`，boot-check 的 uefi 分支不传 `-cdrom`）的 `boot.log` 里**同样**有这 2 行，说明它是 QEMU q35 默认挂的空 ATAPI CD-ROM 设备（无介质、非启动项，固件选择的是 `UEFI Misc Device`）。`install-boot.log` 的 `sr0` 未承载任何 live 文件系统，且 cmdline/根分区均指向 `vda2`。

### 5.5 断言不是空跑：离线重放 + 负例

用**真实** `install-boot.log` 通过 boot-check 自己的断言代码重放（`--log-from`，不启动 QEMU）：

```bash
tools/boot-check.sh --artifact <uefi/disk.img 临时 artifact> \
                    --log-from install-boot.log --timeout 10 --json
# exit 0；result=pass；firmware/grub/kernel/systemd/login 5/5 pass
```

负例（把断言关键词全部替换再重放，验证断言会失败而不是恒真）：

```text
redact 全部 8 个模式 → exit 1，5/5 fail
redact 'Linux version' → exit 1，boot.kernel fail
redact 'login:'        → exit 1，boot.login  fail
redact 单个 'EFI v' / 'UEFI' / 'GRUB' / 'Booting' / 'systemd[1]' / 'Reached target' → 仍 pass
```

最后一行是**设计使然**的 OR 语义（firmware / grub / systemd 各有 2 个可接受模式，kernel / login 各 1 个，见 `tools/boot-check.sh:1175-1191`），不是漏洞；它同时也说明“只抹掉一个词”不足以下结论——把 8 个模式全部抹掉才 5/5 fail，证明断言确实在读日志内容，而不是恒真。

### 5.6 CI 不可绕过

- `.github/workflows/ci.yml` 中 `install-smoke` 步骤 `run: bash tools/install-check.sh …`，shell 为 `bash -e`，**没有** `|| true`、`if: false`、`continue-on-error`（全仓库 grep 0 处）。
- 上传步骤用 `if: always()`（只保证失败也留证据），不改变 job 判定。
- job 的 `success` 由 install-check 的退出码决定；evidence 文件与 job log 内容一致（§1.3 说明）。

| **R9** | **失败路径只有离线伪工具链覆盖** | CI 只跑成功路径；installer 的 `SYMBLE: install failed` 分支、install-check 的 timeout/exit 1/2/3/4 由本地 122 + 15 个用例用伪工具链/伪 QEMU 覆盖，未在 CI 注入真实故障（例如满盘、缺 grub 包）。 |
| **R10** | **证据完整性的其它限制** | `out/install/`（`boot-artifact.json`、`boot.log`、`boot-evidence.json`、`disk.img`）未上传：因此 boot 阶段的 5 条断言只能通过 `install-evidence.json` + `install-boot.log` 离线重放复核（本轮已重放 5/5 通过），拿不到 boot-check 的原始 `boot-evidence.json`；另外 `install-boot.log` 是 `cp` 出来的副本，理论上可能与 `out/install/boot.log` 不一致——但两者由同一函数 `cp`、且内容与 evidence 一致，风险低。 |

### 7.3 额外观察（不影响判定）

1. **工作流超时与计划文档有 5 分钟漂移**：workplan §3 写 `install-smoke` 40 min，实际 `timeout-minutes: 45`。实测 3m12s，无实际影响；建议下次改文档或改配置对齐。
2. **CI 多传了一个 `--workdir out/install`**：workplan §2.3/§3 的命令没有该参数，但它是 `install-check.sh` 契约内的选项（用于保留 `disk.img` 便于诊断），且不影响输出位置（`install.log` 等仍写在 `out/`）。
3. **`xorriso` 的既有告警**：`WARNING: EFI boot equipment is provided but no directory /EFI/BOOT`（ISO 树里没有 `/EFI/BOOT` 目录副本，EFI 内容在 `efi.img` 内）。P0-d2 同样存在，ISO 仍能从 El Torito 正常启动，非本切片问题。
4. **安装后 initramfs 无 fsck**：`install-boot.log` 有 `Warning: fsck not present, so skipping root file system`；同 run 的 `boot-smoke`（P0-c）日志**同样**有该行，属既有 rootfs 组成问题（`e2fsprogs` 未进 initramfs），不是 P0-d3 回归。
5. **构建日志里安装器脚本出现两次**：一次是 `$ mmdebstrap … --customize-hook=…` 命令回显，一次是 mmdebstrap 的 `I: running --customize-hook in shell: sh -c '…'` 回显；`grep -c '^  \$ mmdebstrap'` 为 1，**只构建一次**，非重复写入。
6. **QEMU 默认空 CD-ROM**：见 §5.4 观察，非 ISO 复用；用同 run 的 `boot-smoke` 日志做了对照。
7. **phase 1 的 marker 与 QEMU 终止**：install-check 命中 marker 后立即 `kill -TERM` QEMU，此时安装器已完成 `umount`（`step 7/7` 在 marker 之前），磁盘一致；phase 2 随即在同一 `disk.img` 上启动成功，反证卸载干净。

## 8. 结论

**P0-d3 判定：PASS。**

- **F1 回归 PASS**：本地 61 rust + 121/255/122 builder + 40 boot + 15 install + schema + 17/17 P0-a 全过；同 run 其它 5 个 job 全绿。
- **F2 artifact PASS**：`mode=install`、`iso=live.iso`、`install_device=/dev/vda`、cmdline 含 `sysemble.install=/dev/vda`、`images` 仅 iso。
- **F3 静态 PASS**：安装器脚本/unit 与冻结契约逐条一致；122 个离线用例覆盖命令与失败路径。
- **F4 离线 PASS**：15 个 install-check 用例覆盖两阶段、证据合并、超时与失败。
- **F5 CI install-smoke PASS**：`install.log` 是真实分区/格式化/rsync/grub-install 的串口记录，marker 由安装器输出；`install-boot.log` 是同一块 virtio 盘上安装后系统的真实启动，5/5 断言命中；`install-evidence.json` 与之逐条一致；断言经离线重放与负例验证非空跑。
- **F6 边界 PASS**：变更只落在 `builders/debian/**`、`tools/install-check.sh`、`tools/tests/**`、`.github/**`、`docs/plan/P0-d3-workplan.md`。

**核心真实性结论**：这是一次“live ISO → 空白 6 GiB 磁盘 → 从磁盘 UEFI 启动”的**真实闭环**，不是桩或事后补写的证据——新格式化的根 UUID 在两次独立 QEMU 启动之间传递、安装盘自带的 GRUB 2.12（与 ISO 的 GRUB 2.14 不同）被固件从 virtio 盘加载、安装器写的 `/etc/fstab` 在安装后的系统上成功挂载 `/boot/efi`、安装器在首次启动时因 `ConditionKernelCommandLine` 正确地**没有**再次运行。

**非阻塞问题**（建议后续处理，不影响本次判定）：Calamares GUI（R1）、首次启动配置（R2）、通用化设备/磁盘尺寸（R3）、LUKS/LVM/swap（R4）、桌面安装（R5）、`--removable` 固件兼容性（R6）、CI 缺少失败注入（R9）、ISO/磁盘未上传导致 sha256 不可重算（R8）、`boot-evidence.json` 未单独上传（R10），以及 §7.3 的 5 分钟超时文档漂移与 `xorriso` 既有告警。
